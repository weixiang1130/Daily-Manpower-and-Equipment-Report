# 帳號權限管控規畫（AD 整合，地端 .NET 8 階段實作)

> 目標：**屬於某專案（工地）的人只看得到、也只能更動該專案**；成本管理部與系統管理者保有跨站權限。
> 本文件供資訊處在 .NET 8 API 開發時一併設計；前端已於 v20 完成配套鋪路（見 §4）。
> 相關文件：[`API-CONTRACT.md`](API-CONTRACT.md)（合約，本規畫屬其允許的「後端強化」）、[`MIGRATION-PLAN.md`](MIGRATION-PLAN.md) §7 第 2 項環境決策。

## 1. 現況與缺口

| 項目 | 現況 | 缺口 |
|---|---|---|
| 認證 | 整站單一組 Basic Auth 共用帳密 | 無個人身分，無法問責到人 |
| 授權 | 無——任何登入者可見可改全部工地 | 工地間無權限隔離（僅靠選站防呆） |
| 管理員 | 前端 PIN（防誤觸層級） | 非資安防線；稽核資料僅 UI 隱藏 |

## 2. 目標權限模型（建議）

### 2.1 角色

| 角色 | 可見範圍 | 可做 | 對應人員 |
|---|---|---|---|
| **工地使用者** | 所屬工地（可多個） | 該站申請/回報/名單新增/報表匯出 | 各工地工程師 |
| **成控稽核** | 全部工地 | 上述全部＋稽核模組＋計價鎖定 | 成本管理部 |
| **系統管理者** | 全部工地 | 上述全部＋工地清單維護、批次設定、清空、備份 | 成控指定人員 |
| **唯讀（選配）** | 指定工地或全部 | 僅查詢與報表匯出 | 主管、查帳 |

### 2.2 身分來源：公司 SSO ＋ ERP 權限檢視表（2026-08-05 依資訊處規格書定案）

資訊處已提供 AD SSO API 串接規格書（內部文件，不進本 repo；端點、金鑰等實值見成控內部筆記）。機制分三段：

1. **認證（前端）**：導轉式 SSO——前端把 `RedirectUrl` 包成 Base64 token 導向公司 SSO 驗證頁，驗證完成導回並帶回 token（含 `AccessToken`、效期欄位與 `LoginUser.UserId`＝AD 帳號）
2. **身分（後端）**：後端以 AD 帳號呼叫公司人員資料 API（POST，帶 system／apiKey——**必須由後端呼叫**，避免 CORS 且金鑰不落地前端），取得員工工號、姓名、部門等
3. **授權（後端）**：以工號查 **ERP 權限檢視表**（資訊處已開放兩個唯讀 SQL 帳號）——人員↔專案↔角色由 ERP 統一維護，本系統零維護人員名單，開站時據以過濾可見工地與角色

- 專案↔工地對映：`sites` 表加 `project_code` 欄位（對應 ERP 專案代碼；一次遷移，不影響現行合約）
- 原規畫的 AD 群組制／DB 對映表二案**作廢**——ERP 檢視表制優於兩者（專案成員本來就在 ERP 維護，不必再建平行名單）

## 3. API 層實作要點（.NET 8）

權限全部在 API 層落實，**API 合約格式不變**（回應內容被權限過濾屬合約允許的強化）：

1. `GET ?scope=all`：只回該使用者有權限的工地（master.sites 與 stores 同步過濾）
2. `GET ?site=` / 各寫入 op：檢查該 site 是否在使用者權限內，否則 `403`
3. 稽核資料（`audits[]`）：非成控角色的回應可剝除（前端本就不顯示）——這將把 v13 的「UI 隱藏」升級為真隔離
4. 破壞性 op（`clearSite`/`clearAll`）與 `op:master`/`op:config`：限系統管理者——一併解決現行「伺服器端無權限分級」的安審遺留
5. 操作軌跡：API 層記 log（who/when/op/site/record id）——單一共用帳密時代做不到的問責，AD 化後自然獲得
6. 移除 Basic Auth 與前端 adminPin（或保留 PIN 作次要防誤觸）
7. **後端必須驗證 SSO token 本身**（簽章或向 SSO 驗證 AccessToken），不可只信前端送來的 AD 帳號字串——否則任何人可 POST 他人帳號冒名登入。規格書範例未涵蓋此點，實作時須與資訊處確認驗證方式
8. 人員資料 API 的 `isOnJob`／離職日期欄位應納入判斷：離職人員即使 ERP 檢視表尚未清理也應拒絕

## 4. 前端配套

| 狀態 | 內容 | 與權限的銜接 |
|---|---|---|
| ✅ v20 已完成 | 選站即進工作頁：攔截頁選定工地後直接進「點工申請/回報」 | 消除「選兩次」痛點 |
| ✅ v20 已完成 | **單一工地自動進入**：可見工地只有一個時免選站直進 | **權限過濾後，工地使用者開站零點擊直達** |
| ✅ v22 已完成 | **閒置 10 分鐘自動登出＋登出按鈕**：清工作狀態與管理員模式（資訊處要求）；SSO 階段改為丟棄 token，機制沿用 |  安全基線先行，不等後端 |
| ⬜ 待做（小） | **SSO 導轉處理**：新增 `/auth` 回跳路由——組 RedirectUrl 導向 SSO、解回傳 token、把 AD 帳號交給後端換授權物件 | 導轉式 SSO 需前端配合，此為前端唯一新增改動（其餘仍零修改） |

> **過渡期裁示（2026-07-31）**：權限系統上線前**維持自由跳轉**（右上切換器與總覽照常，所有人可見全部工地），不做「一站一連結」等前端層級的隔離——工地間的可見性隔離一步到位交給 API 層權限過濾（§3 第 1 點），避免過渡期出現「看似隔離、實則可繞過」的中間態。過渡期資料安全由整站 Basic Auth 把守。

## 5. 建議推進順序

1. **已上線（v20）**：前端動線配套（§4 前兩項）
2. **已定案（2026-08-05）**：認證與授權機制（§2.2）——資訊處提供 SSO 串接規格與 ERP 權限檢視表唯讀帳號
3. **待資訊處補齊**：正式環境 system／apiKey 配發、SQL 帳號連線資訊安全遞交、權限檢視表欄位結構、ERP 專案代碼↔本系統工地對映、token 後端驗證方式（§3 第 7 點）
4. **API 開發時內建 §3**：權限過濾與操作 log 一開始就做，比事後補容易；前端同步加 `/auth` 路由（§4 第 3 項）
5. **切換日後**：移除 Basic Auth；權限異動全由 ERP 專案設定管理，本系統無需維護 SOP
