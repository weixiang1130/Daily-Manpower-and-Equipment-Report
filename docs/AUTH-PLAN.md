# 帳號權限管控規畫（AD 整合，地端 .NET 8 階段實作)

> 目標：**屬於某專案（工地）的人只看得到、也只能更動該專案**；成本管理部與系統管理者保有跨站權限。
> 本文件供資訊處在 .NET 8 API 開發時一併設計；前端已於 v20 完成配套鋪路（見 §4）。
> 相關文件：[`API-CONTRACT.md`](API-CONTRACT.md)（合約，本規畫屬其允許的「後端強化」）、[`MIGRATION-PLAN.md`](MIGRATION-PLAN.md) §7 第 2 項環境決策。

## 1. 現況與缺口

| 項目 | 現況 | 缺口 |
|---|---|---|
| 認證 | 整站單一組 Basic Auth 共用帳密 | 無個人身分，無法問責到人 |
| 授權 | 無——任何登入者可見可改全部工地 | 工地間無權限隔離（僅靠選站防呆） |
| 管理員 | 前端 PIN（防誤觸層級） | 非資安防線；稽核資料僅 UI 隱藏 |

## 2. 目標權限模型（建議）

### 2.1 角色

| 角色 | 可見範圍 | 可做 | 對應人員 |
|---|---|---|---|
| **工地使用者** | 所屬工地（可多個） | 該站申請/回報/名單新增/報表匯出 | 各工地工程師 |
| **成控稽核** | 全部工地 | 上述全部＋稽核模組＋計價鎖定 | 成本管理部 |
| **系統管理者** | 全部工地 | 上述全部＋工地清單維護、批次設定、清空、備份 | 成控指定人員 |
| **唯讀（選配）** | 指定工地或全部 | 僅查詢與報表匯出 | 主管、查帳 |

### 2.2 身分來源（2026-08-11 修訂：認證改為內網 Windows 整合驗證）

> **裁示（2026-08-11）**：系統只在公司內網運行，**只有內網環境下的 AD 帳號密碼才能驗證**。
> 因此認證改用 **Windows 整合驗證**（主機層 IIS 啟用 Windows 驗證並停用匿名，
> 或 HTTP.sys 設 Negotiate/NTLM），取代原規畫的導轉式 SSO。
>
> 這一改**消掉了原本唯一的真阻礙**：§3 第 7 點「後端必須驗證 SSO token，否則任何人
> 可 POST 他人帳號冒名登入」——Windows 驗證下後端拿到的是經 Kerberos／NTLM 驗過的
> 網域身分，**沒有 token 可偽造**。連帶不再需要 SSO 端點、apiKey 與前端 `/auth` 路由
> （§4 第 4 項因此取消，前端維持零修改）。
>
> ✅ **已解（2026-08-12）**：權限檢視表的鍵是**工號**不是 AD 帳號，中間需要一次
> 「AD 帳號 → 工號＋部門名稱」對應——**資訊處的人員資料 API（`GetEmployeeByAD`）
> 正好提供**：以 AD 帳號查得 `userId`（工號）、`deptName`（部門，規則 1 依據）、
> `isOnJob`／`leaveDate`（在職判斷）。已在 `IEmployeeDirectory` 的 `HrApiEmployeeDirectory`
> 實作並以假 API（回傳規格書的回應形狀）＋權限檢視表替身跑完整鏈路驗證通過。
> 端點／`system`／`apiKey` 一律由環境變數帶入（機密，不進 repo）。
>
> **認證方式待抉擇**：`Auth:Mode=Windows`（主機層 Windows 整合驗證，無 token 可偽造，
> 直接解 §3 第 7 點）或走規格書的 SSO 導轉流程（需另驗 AccessToken）。
> 規格的 SSO 端點本身即 NTLM，與 Windows 整合驗證同源，建議採 Windows 模式。

以下為原規畫（導轉式 SSO），保留備查；③授權部分不受影響、仍然有效：

#### （原）公司 SSO ＋ ERP 權限檢視表（2026-08-05 依資訊處規格書定案）

資訊處已提供 AD SSO API 串接規格書（內部文件，不進本 repo；端點、金鑰、檢視表與伺服器名等實值見成控內部筆記）。機制分三段：

1. **認證（前端）**：導轉式 SSO——前端把 `RedirectUrl` 包成 Base64 token 導向公司 SSO 驗證頁，驗證完成導回並帶回 token（含 `AccessToken`、效期欄位與 `LoginUser.UserId`＝AD 帳號）
2. **身分（後端）**：後端以 AD 帳號呼叫公司人員資料 API（POST，帶 system／apiKey——**必須由後端呼叫**，避免 CORS 且金鑰不落地前端），取得**員工工號、姓名、部門名稱、在職狀態**
3. **授權（後端）**：以工號查 **ERP 權限檢視表**（資訊處已開放唯讀 SQL 帳號）——人員↔專案↔角色由 ERP 統一維護，本系統零維護人員名單，開站時據以過濾可見工地與角色

- 專案↔工地對映：`sites` 表加 `project_code` 欄位（對應 ERP 專案代碼；一次遷移，不影響現行合約）。**12 個工地已全數完成對映**（2026-08-05 實查 11 站；2026-08-12 補上第 12 站，見下方註記）

> **⚠ 盤點工地清單時的權威來源是線上 API 的 `master.sites`（`GET ?scope=all`），
> 不是 `config.local.js`。** 2026-08-05 的盤點漏了一站，原因有二：①該站是後來直接在
> 系統內新增的，不在 config 的預設候選名單裡；②該站在 ERP 的專案名稱與系統工地名
> 差一個詞尾，純字串比對也對不上。**新增或啟用工地時，務必同步確認其 `project_code`
> 已填**——未填的站不會報錯，只會讓工地使用者看不到它（見 §5 驗收情境 11）。
- 原規畫的 AD 群組制／DB 對映表二案**作廢**——ERP 檢視表制優於兩者（專案成員本來就在 ERP 維護，不必再建平行名單）

### 2.3 ERP 權限資料的形狀（實查確認，決定授權演算法）

權限檢視表的粒度是 **一列＝(專案 × 人員 × 角色)**，一個人在同一專案下**會有多列**（多重角色）。全表約 10 萬列／317 專案／638 人，與專案主檔同批每日重新整理。

角色欄位為 ERP 原生角色名（`RoleName` ＋ 中文 `RoleDescription`），約 28 種，**混合三類**：

| 類別 | 例 | 與本系統的關係 |
|---|---|---|
| **工地職務角色** | 工地工程師、工地主任 | ✅ 決定工地使用者權限 |
| **成控／稽核角色** | 成控、成控管理、稽核 | ✅ 決定跨站權限 |
| 公司／部門別角色 | 公司別代碼、內勤、會計、採購、資金、BI 等 | ❌ **與工地權限無關，一律忽略** |
| 其他職能角色 | 職安、進度管理 | ❌ **不納入**（裁示，見下） |
| 他公司人員角色 | 集團內其他營造/機電公司代碼 | ❌ **不納入**（裁示，見下） |

> ⚠ 實作陷阱：**不可用「這人在此專案有幾列」判斷權限**——大多數列是公司別角色。
> 必須**只挑白名單內的角色名**來判定，其餘忽略。

> **裁示（2026-08-05）**：職安與進度管理人員**不納入**本系統（不填點工單）；
> 集團內其他公司人員**不會使用**本系統。兩者日後若有查詢需求，另議「唯讀」角色，
> 不影響現行判定規則。

### 2.4 授權判定規則（依序比對，第一個命中者為準）

| 順序 | 條件 | 判定角色 | 可見範圍 |
|---|---|---|---|
| 1 | 人員資料 API 的**部門名稱＝成本管理部** | **系統管理者** | 全部工地 |
| 2 | ERP 角色含**成控／成控管理／稽核** | 成控稽核 | 全部工地 |
| 3 | ERP 角色含**系統管理員** | 系統管理者 | 全部工地 |
| 4 | ERP 角色含**工地主任** | 工地使用者（主管） | 該專案對映的工地 |
| 5 | ERP 角色含**工地工程師** | 工地使用者 | 該專案對映的工地 |
| 6 | 以上皆無 | **無權限**（拒絕登入並提示洽成控） | — |

**規則 1 為本專案裁示（2026-08-05）**：成本管理部人員一律預設為系統管理者，
**不依賴 ERP 是否已給該員成控角色**——實查發現部門內有人員未掛成控角色，
若只看 ERP 角色會漏判。部門名稱以**人員資料 API 回傳值**為準（即時、權威）。

> 註：ERP 的成控角色持有者中，有少數人的所屬部門為工地或其他單位。
> 依上表，這些人走規則 2 取得**成控稽核**（全站可見）而非管理者——符合預期。
> 另：工地人員在 ERP 的「部門」欄位常填**工地名稱**而非真部門，故規則 1
> 只認明確的部門名稱，不會誤放行。

### 2.5 過渡期的管理員機制與上線時機

現行前端 adminPin（v13 起）在權限上線後**移除**——管理員身分改由規則 1／3 判定。
在 SSO 上線前，adminPin 維持現狀作為過渡。

> **上線時機裁示（2026-08-05）**：本權限機制**不在公有雲階段啟用**，
> 隨**地端正式上線時一併部署**。理由：SSO 與 ERP 權限查詢皆屬內網資源，
> 公有雲環境無法連線；過渡期資料安全繼續由整站 Basic Auth 把守（§4 過渡期裁示）。
> 因此相關前端改動（`/auth` 路由）亦與地端切換同批發布，不單獨推上雲端。

## 3. API 層實作要點（.NET 8）

權限全部在 API 層落實，**API 合約格式不變**（回應內容被權限過濾屬合約允許的強化）：

1. `GET ?scope=all`：只回該使用者有權限的工地（master.sites 與 stores 同步過濾）
2. `GET ?site=` / 各寫入 op：檢查該 site 是否在使用者權限內，否則 `403`
3. 稽核資料（`audits[]`）：非成控角色的回應可剝除（前端本就不顯示）——這將把 v13 的「UI 隱藏」升級為真隔離
4. 破壞性 op（`clearSite`/`clearAll`）與 `op:master`/`op:config`：限系統管理者——一併解決現行「伺服器端無權限分級」的安審遺留
5. 操作軌跡：API 層記 log（who/when/op/site/record id）——單一共用帳密時代做不到的問責，AD 化後自然獲得
6. 移除 Basic Auth 與前端 adminPin（或保留 PIN 作次要防誤觸）
7. ~~**後端必須驗證 SSO token 本身**~~ **（2026-08-11 已解：改用 Windows 整合驗證，沒有 token 可偽造）**　原文：（簽章或向 SSO 驗證 AccessToken），不可只信前端送來的 AD 帳號字串——否則任何人可 POST 他人帳號冒名登入。規格書範例未涵蓋此點，實作時須與資訊處確認驗證方式
8. 人員資料 API 的 `isOnJob`／離職日期欄位應納入判斷：離職人員即使 ERP 檢視表尚未清理也應拒絕
9. **授權結果快取**：權限檢視表約 10 萬列且每日才更新一次，登入時查一次並快取於 session（建議 30 分～1 小時），不要每個 API 呼叫都查 ERP
10. **角色白名單寫成設定**：§2.3 的角色分類（哪些 ERP 角色算工地／成控／管理者）應為可調設定值，不寫死在程式——ERP 日後新增角色時免改版
11. **無權限者的處理**：規則 6 命中時回 `403` 並帶明確訊息（「您在 ERP 尚無任何專案權限，請洽成本管理部」），前端顯示引導頁而非空白畫面
12. **ERP 連線失敗的降級策略**：權限查詢失敗時應拒絕登入（fail-closed），不可預設放行；並記錄告警

3. ✅ **已實作（2026-08-11，節點 35 階段 D）**：權限判定、API 過濾、稽核真隔離、
   破壞性 op 限管理者、操作軌跡 log、fail-closed。以 `Auth:Mode` 控制，
   **預設 Off**（不啟用＝維持現行行為），資訊處部署時才開啟
4. **待確認（唯一未決）**：AD 帳號 → 工號＋部門的取得方式（查 AD 屬性／人資 API）
   ——見 §2.2 修訂說明。其餘原「待資訊處補齊」項目已因認證方式改變而不再需要：
   token 驗證（Windows 驗證取代）、system／apiKey（同）、正式環境連線資訊（資訊處部署時自行設定）
5. **部署時**：由資訊處在 `appsettings` 設 `Auth:Mode=Windows` ＋ ERP 連線字串，
   並在 `sites.project_code` 填入專案代碼對映
6. **切換日後**：移除 Basic Auth 與 adminPin；權限異動全由 ERP 專案設定管理，本系統無需維護 SOP

## 6. 驗收情境（權限上線前必測）

| # | 情境 | 預期 | 本機驗證（2026-08-11） |
|---|---|---|---|
| 1 | 成本管理部人員登入 | 看到全部工地、具管理員功能（設定／稽核／備份） | ✅ |
| 2 | 單一工地工程師登入 | 只看到該工地、**免選站直接進入**（v20 配套生效）、無管理員功能 | ✅ |
| 3 | 跨兩個工地的工程師登入 | 只看到那兩個工地，切換器只列這兩站 | ✅ |
| 4 | 成控角色但非成本管理部者登入 | 看到全部工地、有稽核模組、無管理員破壞性功能 | ✅ |
| 5 | ERP 無任何專案權限者登入 | 拒絕並顯示引導訊息，不進入系統 | ✅ |
| 6 | 離職人員（isOnJob=否）登入 | 拒絕（即使 ERP 權限資料未清理） | ✅ |
| 7 | 直接 POST 他人 AD 帳號至後端 | 拒絕——**改用 Windows 整合驗證後不再適用**：身分由主機層驗證，前端無從自稱 | ⚠ 需網域環境實測 |
| 8 | 工地使用者直接呼叫他站 API | `403`（§3 第 2 點） | ✅ 讀寫皆已驗 |
| 9 | ERP 連線中斷時登入 | 拒絕並告警，不可放行（§3 第 12 點） | ✅ 回 503 未退化 |
| 10 | 工地使用者的回應不含他人稽核資料 | `audits` 為空陣列（真隔離，非 UI 隱藏） | ✅ |
| 11 | 工地角色但 `project_code` 未填 | 回 200 但工地清單為空（設定沒做完要看得出來，不是擋在門外） | ✅ |

> 本機以 `Auth:Mode=Dev` ＋ LocalDB 上的 `BI.dbo.vw_Acumatica_Permission` 替身驗證
> （欄位與型別照實查結果，含 `UserID` 是 char 有尾端空白這個陷阱）。
> **情境 7 與 Windows 驗證本身需在實際網域環境複驗**——本機無網域可測。
