# 地端移轉計畫（雲端 Netlify → 公司內網 .NET 8 + SQL Server）

> 對象：資訊處與成本管理部。本文件說明**現況**、**目標架構**、**分工**、**資料移轉方式**與**切換日程序**。
> 相關文件：[`API-CONTRACT.md`](API-CONTRACT.md)（後端規格）、[`backend/sql/README.md`](../backend/sql/README.md)（資料層實作）、[`DEPLOYMENT.md`](DEPLOYMENT.md)（Node 可攜式伺服器版部署，過渡/備援用）

## 1. 現況：三個環境，各司其職

| 環境 | 位置 | 角色 | 是否有真實資料 |
|---|---|---|---|
| **正式營運** | Netlify 雲端（前端＋Functions＋Blobs） | **同事每天實際使用中**，唯一的真實資料來源 | ✅ 是（唯一權威） |
| **本機開發／展示** | 成控電腦 SQL Server Express 引擎（LocalDB 執行形態） | 資料表結構驗證、遷移演練、對資訊處展示 | 副本（快照，不接收新資料） |
| **本機 DEMO** | 成控電腦靜態網頁 | 功能展示與測試（示範資料） | ❌ 純假資料 |

**關鍵澄清**：本機資料庫**不是**正在運作的系統，它是「彩排舞台」——用來證明資料表設計可行、遷移腳本可用。同事的每一筆填報都只寫進雲端。

## 2. 目標架構（移轉後）

```
使用者瀏覽器（公司內網）
      │ HTTPS
┌─────┴──────────────────────────────┐
│ 公司 Web 伺服器（IIS / Kestrel）        │
│  ├─ 靜態前端：index.html / app.js /… │  ← 現行前端原封不動
│  └─ API 服務：.NET 8（依 API 合約）    │  ← 資訊處開發（或我方交付參考實作）
└─────┬───────────────┬───────────────┘
      │ SQL           │ 檔案系統
┌─────┴──────┐  ┌─────┴──────────────┐
│ SQL Server │  │ 附件目錄（照片/掃描檔） │
│ 19 表 5 VIEW│  │ 依 attachments.file_path │
└────────────┘  └────────────────────┘
```

**前端零修改**：現行前端僅透過單一接縫 `/api/data` 與後端溝通，且 API 位址可由 `config.local.js` 的 `apiBase` 設定覆寫。只要新後端符合 [`API-CONTRACT.md`](API-CONTRACT.md)，前端不需改一行。

## 4. 資料移轉方式

### 4.1 移轉什麼

| 資料 | 來源 | 目的地 | 工具 |
|---|---|---|---|
| 工地、名單池、單據、回報、稽核紀錄 | 雲端（管理員「下載完整備份 JSON」） | SQL Server 17 張表 | `backup-json-to-sql.py` → sqlcmd |
| **附件檔案本體**（簽單掃描檔、稽核照片） | 雲端（逐一 `GET ?attachment=`） | 公司檔案伺服器目錄 | 逐筆下載 → 回填 `attachments.file_path` |

> ⚠ **最重要的一點**：管理員下載的 JSON 備份**只含附件的描述資料，不含檔案本體**。附件必須另外搬運，否則切換後照片與掃描檔全部連不到。

### 4.2 移轉演練（已完成，非紙上作業）

2026-07-29 以**正式站最新完整資料**在本機 SQL Express 實跑：

| 項目 | 結果 |
|---|---|
| 匯入 | 11 工地／978 名單選項／237 點工單／9 機具單 → **零錯誤、零跳過**（機具回報/逐台明細正式站尚無資料，該三表另以合成資料驗證） |
| 對帳 | 各表筆數與來源備份**完全一致** |
| 多工地隔離 | 各站名單與單據依 `site_id` 獨立，實查驗證 |
| 髒資料防護 | 壞編號／壞日期／壞狀態／缺稽核人／重複選項等自動跳過並分類計數 |

代表：切換日執行的是**已經演練過的腳本**，不是第一次嘗試。

## 5. 三階段時程

### 階段一：API 開發（測試環境）
1. 資訊處配置 SQL Server 測試資料庫 → 執行 `DB-SCHEMA.sql`（一次建好 19 表 5 VIEW）
2. 依 `API-CONTRACT.md` 與 `sql/README.md`（逐操作 SQL 對照、409 寫法）開發 .NET 8 服務
3. 掛上現行前端（設定 `apiBase`）自我驗收

### 階段二：整合驗收（測試環境）
1. 匯入一份雲端備份到測試資料庫（同切換日程序，先演練一次）
2. 跑驗收清單（`DEPLOYMENT.md` §4 步驟 5）：開站、選工地、申請、回報（逐工種＋分段加班）、稽核、報表 CSV、附件開啟、管理員功能
3. **並發測試**：兩個瀏覽器同時編輯同一筆 → 後送出者需收到 409 提示（此為計價正確性的關鍵防線）

### 階段三：正式切換（停機時段，約半天內）
1. 公告停機，暫停填報
2. 雲端：管理員下載**最終**完整備份 JSON
3. **附件搬運**：依備份中 `attachments[].id` 逐一下載檔案 → 存入正式附件目錄 → 回填 `file_path`
4. 轉換並匯入：`backup-json-to-sql.py` → sqlcmd（`-f 65001 -x -b`，腳本內含 `XACT_ABORT` 整批回滾保護）
5. **對帳**：核對各表筆數與計價彙總數字
6. 驗收清單覆跑一次（含附件抽查）
7. 內網 DNS／入口指向新站；公告新網址、更新手冊
8. **舊站保留一段時間**（確認穩定前不下架，隨時可回退）；確認無人使用後再退場 Netlify

## 6. 回退方案

切換後若發現重大問題：**雲端舊站原封不動保留**，把入口切回去即可（幾分鐘）。因此第 8 步「確認穩定前不下架」不可省略。切換期間（步驟 2 之後）的新填報須在切換完成後人工補入——這是停機公告要涵蓋的範圍。

## 7. 待資訊處決策的五項環境事項

1. SQL Server 版本／執行個體／Collation（**DDL 需 2017 以上**，用到 `STRING_AGG`／`OPENJSON`）
2. .NET 8 服務的認證方式（是否整合 AD 網域帳號——建議整合，可解決現行單一共用帳密無法問責的限制；**角色/群組/API 過濾的完整規畫見 [`AUTH-PLAN.md`](AUTH-PLAN.md)**，前端配套已於 v20 完成）
3. 應用程式 DB 帳號與最小權限（僅資料讀寫，不給結構變更權）
4. 內網網址、HTTPS 憑證、反向代理歸屬
5. 靜態前端掛載位置、附件目錄位置與備份策略；名單設定檔 `config.local.js` 的安全遞交方式

## 8. 現行雲端在切換前的定位

- 雲端持續為**唯一正式環境**，同事照常使用，功能持續迭代
- 本機 SQL 副本僅供開發與展示，**不接收新資料**、不對外服務
- 兩者互不影響；正式資料的唯一權威在雲端，直到切換日完成對帳為止
