# 節點 32：機具欄位擴充與計價口徑（v22.6）

## 背景

使用者需求原文：

> 1. 機具申請要增加一欄預定使用時數，才有辦法與實際回報時數有差異性，還要增加一欄備註，
>    因為機具有包月，我們可以直接填寫。
> 2. 機具在申請時不會直接寫廠商，由工地統一叫車再配車，所以回報時需增加一欄「廠商」。
> 3. 機具在回報時可以增加一欄加班時數（出工為一天＋加班時數）這樣，另外回報也要加實際工作內容。

### 順帶修掉的既有缺陷

`updateEquipDiff()` 原本算的是 **`實際使用時數 − 需求數量`**，也就是**拿時數減台數**。
兩者單位不同，算出來的「差異」從一開始就沒有意義；申請 2 台、實際用 8 小時會顯示差異 +6。
合約 §4.4 更把 `requiredQty` 註記為「需求數量=預計使用時數」——欄位說明本身也是錯的。
新增「預定使用時數」正好把這件事一併修正。

## 裁示（2026-08-10）

| 議題 | 決定 |
|---|---|
| 加班時數計價口徑 | **單一欄，不分段**。點工的「前 2 小時／第 3 小時起」分段規則**不適用機具** |
| 出工天數 | **獨立成可填欄位**（0.5／1／2…），非固定 1 天 |
| 申請單的機具廠商欄 | **從申請單移除**，只在回報填 |

## 資料模型（合約 §4.4 已同步更新）

**父層（申請）**

| 欄位 | 變更 |
|---|---|
| `plannedHours` | **新增**。預定使用時數；**空白存 `null` 而非 0**——0 代表「預定就是 0 小時」，null 代表「沒填」，差異計算要分得出來 |
| `applyNote` | **新增**。申請備註（包月等計價前提），支援自動列點 |
| `requiredQty` | 語意不變（台數），但欄名正名為「需求數量(台)」 |
| `vendor` | **申請表單不再填**。舊單保留原值，新單為空字串 |

**子層（回報）**

| 欄位 | 變更 |
|---|---|
| `vendor` | **新增**。實際配到的車行 |
| `days` | **新增**。出工天數 |
| `otHours` | **新增**。加班時數（單一欄） |
| `workContent` | **新增**。實際工作內容，支援自動列點 |
| `diff` | **改為 `actualHours − plannedHours`**；`plannedHours` 為 null 的舊單則為 `null` |

## 有效廠商：一個函式，一處定義

廠商從申請層搬到回報層，等於**每一個讀 `r.vendor` 的地方都可能讀錯**。
因此定義單一權威 `recVendor(r) = report.vendor || vendor`，並把**全部 17 處**呼叫點收斂過去：
清單、清單篩選、歷程報表、報表篩選、計價彙總分組、稽核選單／表單／紀錄／PDF／CSV。

點工的 `report` 不存在 `vendor` 欄位，一律落到 `r.vendor`，所以兩種單據共用同一個函式，
不需要傳 kind。

## 計價彙總

依裁示，機具計價的組成是「出工天數＋加班時數」，兩者**各出一欄**
（計價紅線 4：報表不能只給一個算完的數字）。實際使用時數保留供對帳：

`期間｜機具廠商｜已回報單數｜0使用單數｜總出工天數｜總加班時數｜總實際使用時數｜…`

## 送出前警示（新增三條）

出工天數與加班時數直接進計價，異常值在送出前攔一次：

- 有實際使用時數但出工天數為 0（計價會抓不到日數）
- 出工天數 > 3 天
- 加班時數 > 12 小時

另外回報未填廠商時會提醒一次（不擋送出——現場可能先報時數、廠商稍後補）。

## 後端與移轉

- `backend/sql/DB-SCHEMA.sql`：`equip_records` 加 `planned_hours`／`apply_note`、
  `vendor` 放寬為可空；`equip_reports` 加 `vendor`／`days`／`ot_hours`／`work_content`，
  `diff` 放寬為可空。兩個 VIEW 改用 `COALESCE(rep.vendor, r.vendor)`
  並加上 `total_days`／`total_ot_hours`
- 新增篩選索引 `IX_equip_rep_vendor`；舊的 `IX_equip_vendor` 改為 filtered index（僅舊單有值）
- `backup-json-to-sql.py` 同步新欄位；**`diff` 改為可為 NULL，不再塞 0**——
  0 在報表上會被讀成「相符」

## 驗證：65 項自動檢查全過

**欄位與報表（32 項）**：有效廠商四種情境（新制／舊制回落／未填／點工不受影響）、
計價彙總可心算、明細欄位、差異計算、清單顯示、匯出全量、自動列點沿用。

驗算式（可心算）：

| 廠商 | 組成 | 總出工天數 | 總加班時數 | 總實際使用時數 |
|---|---|---|---|---|
| 車行甲 | E1(1 天/2h/6h) ＋ E2(0.5 天/1h/8h) | 1.5 | 3 | 14 |
| 車行乙 | E3 舊制單（無天數與加班） | 0 | 0 | 4 |

**表單送出（17 項）**：實際觸發 submit 並攔截 `fetch`，驗證真正序列化後送出的 JSON。
涵蓋預定時數留空存 null、**編輯舊單不可洗掉既有廠商與既有回報**、差異對預定時數計算。

**匯出（16 項）**：明細 CSV 含全部新欄位、舊欄名已移除、**翻到第 2 頁仍匯出全量 4 筆**、
多行內容加引號；彙總 CSV 車行甲 `1.5,3,14`。

**版面**：機具清單 1,306→1,498px、明細 26 欄，四種視窗寬下壓欄／折行皆為 0。

### 驗證過程的兩個插曲

1. **`apiSaveRecord` 攔不到**：它是 `const`（在 script 的語彙範圍，不掛在 `window` 上），
   指定 `window.apiSaveRecord` 只是造出一個沒人讀的影子屬性。改攔 `window.fetch`
   反而更忠實——驗到的是真正送出去的 JSON。
2. **假的 GET 回應把快取清掉**：測試用的 fetch stub 對 GET 也回 `{v:1}`，
   背景校正（`bgRefetchVerify`）拿到空資料就把 `SITE_CACHE` 清了，
   後續操作誤判「此紀錄已被其他人刪除」。stub 要照實回目前快取。

## 相容性

- 舊機具單（無 `plannedHours`／`days`／`otHours`）完全可讀：差異顯示「未填預定」而非 0，
  天數與加班以 0 計入彙總
- 編輯舊單時申請廠商原樣承繼，不會因為表單上看不到就被洗成空字串
- 稽核的 `applied` 快照仍是 `requiredQty`（台數），現場實點的也是台數，語意一致

## v22.9 補強：機具使用時數不再預填 8 小時

### 問題（Scott 回報）

> 「假設他申請寫 4 小時，實際只使用了 1 小時，但現在是你回報點機具，
> 他會直接鎖定 8 小時，這樣是不對的，應該是要讓工地可以根據使用情境
> 去填寫他們使用多少時間。」

回報表單勾選機具時，逐台的「使用時數」會自動填 **8**；而總計「實際使用時數」
欄位是**唯讀**的（由逐台加總而來）。使用者看到的就是「一勾就鎖 8 小時」。

這會直接算錯錢：機具若綁到**時租**品項，計價是 `實際使用時數 × 單價`
（見合約 §4.9）。申請 4 小時、實際只用 1 小時的單子，只要沒人特地去改逐台欄位，
就會以 8 小時進計價。

**正式資料實查**：已勾選到場的機具明細中，剛好等於 8 小時的佔 **20%**，
最多的是 11 小時（23%），分布範圍 4～19 小時——多數人確實有去改，
但仍有五分之一卡在預設值上，這些單值得回頭抽查。

### 改法

**系統不猜數字。** 勾選時不預填，欄位留白並顯示 placeholder「請填寫」。

關鍵是把「空白」與「0」分成兩件事——改版前 `parseFloat("")||0` 讓兩者都變成 0：

| 狀態 | 意義 | 處理 |
|---|---|---|
| 空白（`null`） | 還沒填 | **擋下送出**，訊息點名是哪幾台沒填 |
| `0` | 確實填了 0 | 沿用既有的異常警告，可確認後送出 |

若放行空白，會靜默變成 0 小時進計價——是另一個方向的錯帳。

**新檢查必須擺在既有「時數為 0」那道之前。** 單台機具沒填時總計也是 0，
會先被那道攔下並叫使用者去勾「0 使用確認」——那是錯的指引，
他其實是勾了到場卻忘了填時數。（實測時就是先寫成錯的順序才發現。）

**沒有改成預填「預定使用時數」**：那會重蹈覆轍——使用者照樣接受預設值不看。
預定時數已顯示在表單上方的單據資訊列，要對照隨時看得到。
（另外預定時數是整張單的總時數、不是每台的，逐台預填也會誤導。）

### 驗證（以地端 API 供應真實資料，瀏覽器實際操作）

- 勾選後時數欄**空白**、總計 0；填 1 → 總計 1；改 0.5 → 總計 0.5
- 清空欄位 → 回到「未填」而非 0；取消勾選再勾一次仍不會冒出 8
- 單台空白送出 → 擋下，訊息為「請填寫實際使用時數：（機具名）」
  而**不是**叫人去勾 0 使用確認
- 兩台其一空白 → 擋下並點名空白那台（正式資料無多類型機具單，此案以
  同一段渲染／送出邏輯模擬第二列）
- 明確填 0 → 經異常警告確認後可送出，存進去就是 0
- **既有已回報單重開，原本的時數原樣帶出**（實測 10 小時的單仍是 10）
- 全程以攔截 `fetch` 驗證送出內容，未寫入資料庫；事後查核各表筆數不變

## v22.9.1 補強：修 v22.9 的副作用 ＋ 申請可選填廠商

### 一、機具回報「實際使用時數變成 0 且改不動」（Scott 回報）

v22.9 把逐台「使用時數」改成不預填（正確），但留下兩個副作用疊在一起：

1. 開回報表單時「實際使用時數」總欄被**預設成 0**（`loadEquipReportRecord` 舊寫法 `: 0`）
2. 只要單據有機具類型，總欄就是**唯讀**的（由逐台加總）——單台時使用者看到唯讀的 0、
   改不動，而真正的輸入格（逐台那個小欄位）不起眼、不會注意到

**根因盤點**：計價（時租）用的是總時數 `rep.actualHours`，**不是逐台時數**；
正式資料中**一張多類型機具單都沒有**。所以「逐台拆時數」對實務幾乎是多餘的，
卻正是這次卡住的來源。

**改法**：
- 總欄開表單時**留空白**而非 0
- **單台**（實務上的全部情形）與無類型：總欄**直接可編輯**，輸入即寫回該台；
  填了時數自動補勾「到場」；旁邊顯示「時數請填於下方『實際使用時數』↓」引導
- **多台**（罕見／目前無）：維持逐台輸入＋唯讀加總，且全部未填時總欄顯示空白而非 0
- v22.9 的「勾到場卻沒填時數就擋下並點名」保留；「空白≠0」的分野保留

### 二、機具申請可選填廠商（Scott 要求「跟點工一樣有地方填廠商」）

v22.6 曾把廠商從申請移到回報（理由：工地統一叫車後才配車、申請當下未知）。
現改為**兩段皆可**：申請時已知車行就先填（**選填**），否則留白、回報時再填。

- 資料模型未動：`equip_records.vendor` 本就可空；計價分組一律走 `recVendor()`
  （**回報值優先於申請值**），所以先填後改不會衝突
- 申請表單新增選填廠商 combobox；編輯申請單時原值原樣帶回

### 驗證（以地端 API 供應真實資料，瀏覽器實際操作）

- 開回報表單：總欄空白、可編輯、單台不再有逐台小欄
- 直接於總欄填 1／改 0.5／清空 → 即時寫回，清空回「未填」；填值自動補勾到場
- 送出：填 3 小時 → 存進去就是 3（不是 8 也不是 0）
- 勾到場但總欄空白 → 擋下，訊息「請填寫實際使用時數：（機具）」
- 多台（模擬）：逐台輸入保留、總欄唯讀加總（3＋2＝5）、全空顯示空白
- 申請表單：廠商欄存在且選填；填後進 `record.vendor`、`recVendor()` 帶得出來
- 全程攔截 `fetch` 未寫入；事後查核 equip 各表筆數不變
