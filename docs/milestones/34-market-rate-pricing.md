# 節點 34：行情通報單價帶入計價（v22.8）

## 背景

使用者需求：

> 工地回饋希望可以結合行情通報的單價，然後選擇該廠商如果是我們行情通報的廠商，
> 就可以自動在計價的時候帶入金額，不論是點工還是機具都需要參考這個行情通報 excel，
> 這個是按季更新的，所以應該要有更新或是抽換的機制。考量未來在公司內網上，
> 也要有辦法不透過 IT，管理員就可以透過匯入行情通報表就可以更新租工/機具的單價。

公司按季發布兩份 xlsx（租工 188 項、機具 1,499 項），管理員自行匯入，不經 IT。

## 動工前的可行性盤點

需求假設「選了廠商就自動帶入」，但實測**系統廠商名與行情通報供應商名完全同名者為 0**。
原因不是對不上，是**命名層級不同**：系統用工地自己輸入的簡稱，行情通報用公司全名。
改用前綴比對：

| | 唯一命中 | 涵蓋單據 | 命中多家（歧義） |
|---|---|---|---|
| 點工／租工 | 14／17 家 | **562／579 筆＝97%** | **0** |
| 機具 | 9／11 家 | 110／194 筆＝57%※ | **0** |

※ 機具偏低是因為有一個佔位字被用了 82 筆，扣掉後命中率相當高。
**零歧義**是關鍵——代表前綴比對不會綁錯，只會漏綁。

順帶查到系統內有幾組**同音錯字的廠商名**（會讓同一家的計價被拆成兩筆），已回報使用者。

## 三項裁示（2026-08-10）

| 議題 | 決定 |
|---|---|
| 同廠商同工種多個價格（依適用工地不同） | **每個工地綁定一次** |
| 單價來源 | **依出工日查當季費率**（單據不存金額） |
| 實作範圍 | 一次做完租工與機具 |
| 機具品項對照 | **只綁到廠商層級**，實際品項由工程師回報時從該廠商清單挑 |
| 機具加班費率（在來源檔是獨立的列） | **工程師挑兩次**：主品項一項、加班費率一項 |

## 技術：純前端讀 xlsx

xlsx 就是 ZIP，Excel 存出來一律 DEFLATE，用瀏覽器內建的
`DecompressionStream('deflate-raw')` 解，維持零依賴。

**踩到的坑**：Excel 存出來的檔含**上百萬個自閉合空列**（實測 104 萬個、
sheet1.xml 解壓後 40MB），先用 `<row>` 切塊會建出上百萬個物件、瀏覽器直接卡死。
改成**只掃有值的儲存格**，列號從 `r="C5"` 反推，空列完全不碰：

| | 檔案 | 解壓 | 掃格 | 讀出 |
|---|---|---|---|---|
| 租工 | 2.6 MB | 123 ms | 14 ms | 188 列 |
| 機具 | 2.7 MB | 118 ms | 30 ms | 1,499 列 |

**另一個會算錯錢的坑**：Excel 序列日期的起點是 **1899-12-30** 不是 1900-01-01
（沿用 Lotus 的 1900 閏年錯誤）。用錯會整整差兩天，跨季時就抓到上一季的費率。

## 費率解析

**租工**把費率寫在品項文字裡，且有三種寫法，解析器都要吃：

```
打石工3,000元/工、加班前2hr=499元、第3hr起=623元   ← 分兩段，正好對上系統的前2h／第3h起
打石工2,800元/工、加班466元/HR                      ← 單一費率
打石工2,800元/工、打石工加班466元/HR                ← 前綴帶工種名
```

沒寫「第 3 小時起」者視為不分段（`otOver = ot2`）。188 列中 22 列不是費率列
（如「各工種每工統一加保加價費」），匯入時濾掉。
品項內的每工單價與「單位價格」欄**實測 166/166 完全一致**。

**機具**的加班費是獨立的列，計價單位需從品項文字＋單位欄判定：
`全天 455／加班 392／時租 237／半天 203／月租 150／趟次 62`。

## 資料流

```
管理員匯入 xlsx ─→ 前端解析 ─→ op:rateBook（整季覆蓋）─→ blob "rates"
                                                              │
工地綁定（config.rateBindings）───────────────────────────────┤
                                                              ▼
報表／彙總 ── 依出工日取「生效日 ≤ 出工日」最新一季 ── 計算金額
```

- 費率書**刻意不放進 `scope=all`**：一季 1,500 列、多季累積數 MB，
  塞進開站全量讀取會拖慢每個人。改走獨立端點 `GET ?rates=1`，用到才抓
- 以 `effectiveFrom` 為季別唯一鍵：同生效日重匯即取代（可補修正檔），
  不同生效日並存；上限 12 季（三年），超過丟最舊的
- **綁定鍵用「供應商編號＋說明」**，不可用品項文字——租工的品項把價格寫在裡面，每季都會變

## 計價紅線的落實

**查不到費率一律回 `null` 並附原因，絕不退化成 0**——0 在計價表上會被讀成「免費」，
是最難發現的錯。彙總另設「未能計價單數」欄，算不出的單獨立計數而非併入金額。

涵蓋的情境：未綁定、該出工日無適用季別、本季查無綁定的費率列、未挑品項、
本季查無所選品項、有加班時數但未選加班費率。

金額同時附組成說明（`3工×3000＋前2h 2×499＋3h起 1×623`）——計價紅線 4：
報表不能只給一個算完的數字。

## 驗證：54 項全過

**前端端到端 26 項**（用真實的兩份 xlsx）：
- 解析：188→166 可用／略過 22、生效日轉正、分段 91 筆、機具 1,499 列全數分類
- 匯入後的費率列**只保留計價需要的欄位**（聯絡人姓名電話等不進資料庫）
- 金額可心算：租工 `3×3000＋2×499＋1×623 = 10,621`、機具 `2×13000＋3×2000 = 32,000`
- 季別選用：8/5 的單用 Q3、11/20 的單自動改用 Q4（`3×3500＋2×583＋1×583 = 12,249`）
- 六種查無費率情境全部回原因而非 0
- 報表明細、計價彙總的金額欄與「未能計價單數」

**後端 op 邏輯 28 項**（cloud 14 ＋ onprem 14，**兩邊行為完全一致**）：
同生效日取代／不同生效日並存／排序／三種 400 驗證／400 後不動既有資料／
保留上限 12 季且丟最舊／刪除冪等／不影響另一 kind。

## 已知限制

- 上述測試的儲存層是記憶體墊片，**真正的 Netlify Blobs 行為未驗**
  （strong consistency、大物件寫入）；上線後仍需實際匯入一次確認
- 綁定介面只列「本工地實際用過的廠商×工種」，沒用過的不會出現（避免上百筆空綁）
- 機具品項下拉會列出該廠商全部品項（多的有數十項），工程師需自行辨識——
  這是「綁廠商而非綁品項」的取捨
