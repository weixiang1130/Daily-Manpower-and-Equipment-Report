# 節點 35：地端 .NET 8 API — 階段 A～D（合約全端點＋權限機制）

## 背景

地端遷移的最後一塊拼圖是 API 服務。原本的 `backend/onprem/server.mjs` 需要 Node 執行環境，
但公司主機沒有 Node、只有 .NET 8 SDK，資訊處也建議以 .NET 開發。因此以 .NET 8 Minimal API
重寫同一份合約（`docs/API-CONTRACT.md`），前端一行都不用改。

分階段推進，每階段都要能獨立驗收：

| 階段 | 範圍 | 狀態 |
|---|---|---|
| **A** | `GET ?scope=all`、`GET ?site=`、靜態前端 | ✅ 本節點 |
| **B** | `op:record`（含 409）、`master`、`config`、`addOption`、`deleteRecord` | ✅ 本節點 |
| **C** | 附件上下載、行情通報費率書、清空二 op | ✅ 本節點 |
| **D** | 身分與權限過濾（見 `AUTH-PLAN.md`） | ✅ 本節點 |

## 先補上 v22.8 的 SQL 缺口

動工前發現 **節點 34 改了合約卻沒改 `DB-SCHEMA.sql`**：`rateItem`／`rateOtItem`、
各站 `rateBindings`、以及費率書本身在 SQL 都沒有落點。若照原樣移轉，這三樣會**靜默消失**
（前端讀不到綁定＝所有計價變成「未能計價」，但不會報錯）。

補上：

- `equip_reports` 增 `rate_item`、`rate_ot_item` 兩欄
- 新增 `rate_books`、`rate_book_rows`、`site_rate_bindings` 三表
- `backup-json-to-sql.py` 同步輸出上述欄位與 `site_rate_bindings`

資料表數量 11 → **14 表 5 VIEW**。

> 教訓：合約與 DDL 是**同一件事的兩面**，改欄位必須兩邊一起改。
> 已在 `API-CONTRACT.md` 開頭加註提醒。

## 實作決策

**不用 EF，直接 ADO.NET（`Microsoft.Data.SqlClient`）。**
合約的 JSON 形狀是固定且巢狀的，ORM 的物件關聯反而要多一層轉換；直接寫 SQL 能逐句對照
`sql/README.md`，出問題時查得動。

**`InvariantGlobalization` 不可開。**
實測設為 `true` 時 `SqlConnection.Open()` 直接丟 `NotSupportedException`。
中文定序與日期格式本來也需要完整 globalization——部署到 Linux 容器記得裝 ICU。
已在 `.csproj` 留註解。

**日期一律本地字串。**
沿用計價紅線第 2 條：`DateStr()` 走 `DateTime` 的本地格式，**絕不 UTC 化**。
UTC 會把台灣早上記成前一天，直接改變計價月份。

**未實作的操作一律回 501，不可默默回 200。**
前端寫入是 await-first：收到 2xx 就清空表單。當時尚未實作的 `POST /api/data`
若默默回 200，使用者填的資料會直接消失。故對 `POST`、`?attachment=`、`?rates=1`
三處明確回 501。（階段 B／C 完成後這三處都已實作，不再有 501 分支。）

**同一服務供應靜態前端。**
與 `server.mjs` 同樣的部署形態，前端因此是同源呼叫、不需要 CORS。
靜態根寫死指向 `frontend/`，可用環境變數 `STATIC_DIR` 覆寫——
**不可指向 repo 根或 `backend/`**，那會把後端原始碼與 SQL DDL 一併對外提供下載。

## 驗證

**1. 逐欄比對：以正式資料快照為基準，比對地端 API 與雲端 API 的 `scope=all` 回應。**

996 筆單據＋12 站 config 全數逐欄比對。真實差異 **0 處**。
另有兩類「形狀差異」判定為等價並記錄在案：

- 合約標示可缺省的鍵（`audits`／`attachments`／`lockDate`／v22.6 新欄位…）：
  雲端在空值時不輸出，地端一律輸出空值。前端兩者都走 falsy 判斷。
- 某張只有 `totalOT` 的舊單：地端依合約 §4.3 歸段規則把時數明寫進前 2h 段。
  比雲端的隱含更明確，且與計價紅線第 1 條一致。

**2. 端到端開站：把前端指向本服務，實際操作。**

12 工地、683 筆點工、313 筆機具、83 筆附件全數渲染；六個頁籤都正常。

單一工地的計價彙總與 SQL 直查逐項對帳：

**3. 路徑外洩檢查**：`/appsettings.json`、`/Program.cs`、`/../backend/sql/DB-SCHEMA.sql` 皆回 404。

# 階段 B：寫入端（合約 §3.1～§3.5）

## 實作決策

**409 靠資料庫的鎖，不是靠應用層的先讀後寫。**
`op:record` 的「讀版本 → 比對 → 覆寫」整段包在一個交易裡，取版本時加
`WITH (UPDLOCK, HOLDLOCK)`。兩人同時送出時後者會**等前者提交**，因而讀到新的 `v`
而正確吃到 409。若只是 `SELECT` 再 `UPDATE`，兩人可能都讀到舊 `v` 而雙雙寫入——
409 就形同虛設，而且是**靜默**的：兩邊都看到「儲存成功」，先送出的人的內容無聲消失。

**寫入採整筆砍掉重建，附件描述資料例外。**
合約語意是「覆寫整筆」，逐欄 diff 反而容易漏掉被移除的子層（工種列、稽核、附件）。
但附件的 `file_path` 是切換日由搬運腳本補填的，砍掉重建會把它抹成 NULL，
**之後就找不到實體檔案了**。作法是刪除前先快照 `attachment_id → file_path`，
重建時帶回來。

> ⚠ 階段 C 的 `op:deleteAttachment` 實作時要能**只憑 attachment_id 刪實體檔案**，
> 不可依賴 metadata 列還在——前端是「先存單、再刪被移除的附件」，
> 存單當下那列就已經沒了。

**工地找不到時建檔，不回 400。**
雲端版任何工地字串都能直接寫入（blob key 即建即用）。這裡若不比照，
「工地清單還沒同步就先送單」會整筆 400——資料就掉了。新建一律 `is_active=1`，
是否上線由 `op:master` 的清單決定。

**`op:master` 把不在清單裡的工地標 `is_active=0` 而不是刪除。**
退場專案的歷史紀錄還要供成本部查帳。

**不做伺服器端鎖單／權限檢查。**
維持與雲端相同行為（鎖單、管理員皆為前端管控）。這是**既有的已知限制**，
不在本階段擴大也不在本階段修補——要修是階段 D 連同 SSO 一起做，
否則地端與雲端行為分歧，過渡期兩邊並行時會出現「同一操作在 A 可以在 B 不行」。

## 驗證（105 項全過）

**往返保真（81 項）**：送一筆欄位全滿的點工單（父層 8 欄＋子層 18 欄＋逐工種 2 列＋
稽核 1 筆含附件＋父層附件），寫入後逐欄讀回比對。機具單另驗 v22.6/v22.8 新欄位。
其中兩項是刻意設計的陷阱：

- 只有 `totalOT` 的舊單 → 全數歸前 2 小時段（計價紅線 1）
- 機具未填預定時數時 `diff` 維持 `null` ——**不可塞 0**，0 在報表上會被讀成「與預定相符」，是假訊息

**真正的並發（6 項）**：12 條執行緒以 `Barrier` 同時起跑、用同一個 `baseV` 送出。
結果：**恰好 1 人成功、11 人收到 409 modified**；資料庫只留一筆、`v=2` 不跳號、
落庫的是勝出者寫的值、失敗的並發沒有留下殘缺子層。

**其餘（18 項）**：`op:config` 整包覆蓋語意（被移除的項目要消失）與名單去重、
費率綁定兩種形狀（labor 是 `{vendorCode,note}`、equipment 是字串）、
`op:master` 排序與下線不刪資料、`addOption` 合併與 people 單一人名檢查、
id 格式驗證、`deleteRecord` 冪等與子層連坐、未知 op 回 400。

測完刪除拋棄式工地，並確認正式工地數量未受影響；重跑兩份測試結果相同（無殘留）。
階段 A 的全量逐欄比對重跑亦無變化。

# 階段 C：附件、費率書、清空（合約 §2.3／§2.4／§3.6～§3.10）

至此**合約的每一個端點都已實作**，只剩階段 D 的 SSO／權限。

## 實作決策

**附件本體放檔案系統，不進資料庫。**
幾百 MB 的簽單照片塞進 DB 會讓備份與還原又慢又大，而且沒有好處——這些檔案上傳後
不再變動，也不需要交易保護。`file_path` 存**相對於附件根目錄**（環境變數 `ATTACH_DIR`）
的檔名而非絕對路徑：附件目錄搬家時只要改環境變數，不必回頭改幾百列路徑。
檔名一律用已驗證格式的 `attachment_id`（`^[A-Za-z0-9_-]{1,64}$`），
所以不可能出現 `..` 或路徑分隔字元——路徑穿越在來源就被擋掉。

**`deleteAttachment` 只憑 id 刪檔，不查表。**
前端的順序是「先存單（被移除的附件當下就從資料表消失）→ 再呼叫 deleteAttachment」。
若要先查表才刪檔，那些檔案會全部變成孤兒永遠留在磁碟上。反過來，`op:record`
存單時若發現檔案已在磁碟上就自動補 `file_path`（前端是先上傳後存單，
存單當下那一列還不存在）。

**只有描述資料、沒有本體的舊附件回 404 並說明「尚未搬運」。**
遷移進來的 83 筆附件都是這種狀態（備份 JSON 不含檔案本體）。
講清楚是「還沒搬運」而不是「不存在」，否則切換日會被誤判成資料遺失。

**`clearAll` 的刪除範圍對齊雲端。**
雲端是「列出 store 裡所有 blob 全刪」，包含 `master`、各站 `cfg2` 與費率書。
我原本只刪紀錄與附件，比對雲端實作後才發現範圍不足——地端清完會留著工地清單
與名單池，兩邊行為不一致。已改為整庫清空。（`clearSite` 則維持不含 config，合約明訂。）

**仍不加伺服器端權限檢查。**
合約 §3.8 雖明文允許這項強化，但前端管理員設定頁有「清空全部工地資料」按鈕會直接
呼叫它；單方面擋掉會造成地端與雲端行為分歧。ADMIN_TOKEN 一案仍**待裁示**。

## 驗證

**階段 C 本身 63 項全過**：型別白名單／4MB 上限／壞 base64／空內容／壞 id 五種
拒絕路徑；上傳→存單→下載的**位元組完全相同**，Content-Type 與 UTF-8 檔名正確；
`deleteAttachment` 在描述資料已消失時仍刪得掉實體檔案；費率書同生效日整季取代、
不同生效日並存、12 季上限丟最舊、單價 ≤ 0 的列濾掉、`otParsed=false` 原樣保留、
兩種 kind 各自只帶自己的專有欄位；`clearSite` 不動 config 與費率書。

**`clearAll` 另建拋棄式資料庫測（14 項全過）**，全程不碰 `KG_AUDIT_STAGING`。

## ☠ 事故記錄：測試把 STAGING 清空了

階段 B 的測試裡有一段迴圈，斷言「這六個 op 應回 501」，其中包含 `clearAll`。
階段 C 把 `clearAll` 實作出來之後，**同一行就從斷言變成了真的整庫清空**——
`KG_AUDIT_STAGING` 被自己的測試清光。

- **影響**：僅本機測試庫；所有請求都打 localhost，**雲端正式資料完全未受影響**
- **復原**：照 `backend/sql/README.md` §5 的正式程序從備份 JSON 重建，
  各表筆數與計價總數（逐工種 work 1,794／前2h 2,933／第3h起 3,442）與清空前完全一致
- **教訓**：「斷言某 op 尚未實作」這種測試會隨著實作進度**自己反轉語意**，
  對破壞性 op 特別危險。破壞性 op 一律只在拋棄式資料庫裡測，
  正式庫的測試腳本裡不得出現 `clearAll`

（順帶一提：重建時第一次沒加 `-f 65001` 導致 DDL 解析失敗——
`backend/sql/README.md` §5 早已載明這個旗標，是我沒照交付包走，交付文件本身無誤。）

## 已知限制

- 無伺服器端鎖單與權限檢查（與雲端同，待階段 D）
- 遷移進來的 83 筆附件只有描述資料，**切換日仍需另行搬運檔案本體**並補 `file_path`
- Basic Auth 沿用單一共用帳密（與雲端相同），真正的個人身分要等階段 D
- 連線字串預設指向本機 LocalDB 的 `KG_AUDIT_STAGING`（測試庫）；
  正式環境務必以環境變數 `KGAUDIT_CONNECTION` 覆蓋

# 階段 D：身分與權限（合約允許的「後端強化」，格式不變）

## 認證方式改變：導轉式 SSO → 內網 Windows 整合驗證

**Scott 裁示（2026-08-11）**：系統只在公司內網運行，只有內網環境下的 AD 帳號密碼才能驗證。

這一改**消掉了原本唯一的真阻礙**。原規畫的導轉式 SSO 有個沒解的問題（`AUTH-PLAN` §3 第 7 點）：
規格書範例直接相信前端送來的 AD 帳號字串，**任何人都能 POST 別人的帳號冒名登入**，
而資訊處尚未提供 token 驗證方式。Windows 驗證下後端拿到的是經 Kerberos／NTLM 驗過的
網域身分，**沒有 token 可偽造**——問題不是被解決，是不存在了。

連帶不再需要：SSO 端點、apiKey、前端 `/auth` 路由（前端維持**零修改**）。

**刻意不引 `Microsoft.AspNetCore.Authentication.Negotiate` 套件。**
該套件 8.0 線（含最新的 8.0.20）仍帶兩則高嚴重性弱點告警
（GHSA-2p3q-h3hg-jcqq／GHSA-8prm-248r-h957）。把高風險告警帶進交付包給資訊處，
不如把驗證交給主機層（IIS 啟用 Windows 驗證並停用匿名，或 HTTP.sys 設 Negotiate/NTLM）
——本程式只讀已驗證的 `HttpContext.User`。**零相依、零弱點**，而且驗證方式由資訊處
用他們既有的工具管理，本來就該是他們的權責。專案目前**沒有任何已知弱點相依**。

## 三段可抽換的接縫

```
① 認證  誰在連線          IIdentitySource     → AD 帳號
② 目錄  這個帳號是誰      IEmployeeDirectory  → 工號＋部門名稱
③ 授權  這個工號能看哪些站 Authorizer          → 角色＋可見工地
```

**②是唯一還沒定案的一段**：權限檢視表的鍵是**工號**（`UserID`）不是 AD 帳號。
兩條路——查 AD 的 `employeeID`／`department` 屬性（零外部依賴），或呼叫人資 API
（需資訊處配發 system／apiKey）。做成介面之後，兩條路都只是換一個實作，①③不受影響，
所以**不必等答案就能把其餘全部做完**。

## 實作決策

**預設 Off。** `Auth:Mode` 預設 `Off`＝完全維持現行行為。部署新版**不會**因為程式碼裡
有權限機制就突然把人擋在外面；要啟用是資訊處在設定檔改一個字。

**判定規則照 §2.4 的順序，且規則 1 先於 ERP 查詢。**
部門名稱＝成本管理部即為管理者，不查 ERP——實查發現部門內有人未掛成控角色，
只看 ERP 角色會漏判。副作用是**成本管理部人員在 ERP 斷線時仍能正常使用**。

**角色白名單寫成設定不寫死。** ERP 日後新增角色時改設定即可，免改版。
⚠ 實作陷阱：**不可用「這人在此專案有幾列」判斷權限**——大多數列是公司別角色
（光 `K02` 就三萬多列）。必須只挑白名單內的角色名。

**`master.sites` 與 `stores` 必須同步過濾。** 只濾清單而 stores 照給，
等於資料還是送到瀏覽器了，那是「看起來隔離」而不是隔離。

**稽核資料剝除但保留空陣列。** v13 的成控稽核對工地端是**前端隱藏**，資料照樣傳到
瀏覽器；這裡降級為真隔離。但 `audits` 鍵要留著且是陣列——塌成 `null` 會讓前端 `.map` 爆炸。

**fail-closed。** 授權查詢失敗一律拒絕（503）。放行比擋住危險得多——
ERP 一斷線就變成全員全站可見，而且沒有人會發現。

**工地角色但專案對不上 → 空清單而非拒絕。** 多半是該站 `project_code` 還沒填。
使用者看到「沒有可用工地」比被擋在門外容易查出是設定沒做完。

**`UserID` 是 `char` 型別、有尾端空白**，不 `LTRIM(RTRIM())` 會查不到任何列——
而且是靜默的：查無資料看起來就像「這個人沒有權限」。

## 驗證（27 項全過）

本機沒有網域也連不到公司內網的 `BI` 庫，所以在 LocalDB 上建了一個同名的
`BI.dbo.vw_Acumatica_Permission` 替身——欄位、型別（含 `UserID` 是 char 有尾端空白）
與角色體系都照實查結果做，讓整條鏈路**真的跑一次 SQL**，而不是用假物件跳過。
測試資料裡混入公司別（`K02`）、職安、進度管理等雜訊角色，驗證它們確實被忽略。

涵蓋 `AUTH-PLAN` §6 的情境 1～6、8～11，另加：

## 階段 D 續：人資 API 目錄（AD 帳號 → 工號＋部門）實作完成

節點 35 階段 D 當時把「AD 帳號 → 工號＋部門」列為唯一未定案的一段
（`IEmployeeDirectory` 只有設定檔假名單版）。資訊處的 AD SSO 規格書 v2 提供了

### 實作

`HrApiEmployeeDirectory`：POST 人資 API、解析 `data[0]`。以 `Auth:Directory` 切換
（`config`＝假名單／`hrapi`＝人資 API）。端點／`system`／`apiKey` 一律由環境變數帶入，
**絕不寫死**；金鑰只由後端持有（規格要求：避免 CORS 且不落地前端）。

### 認證方式的抉擇（待資訊處確認主機能否開 Windows 驗證）

## 補強（2026-08-12）：交付前 code review 修正 10 項

移交資訊處部署前，對 `backend/onprem/dotnet/` 做了一次高強度 code review。
單據主線的跨工地隔離做得完整，但**附件與子層刪除這條支線整條漏掉**——
共同的根因是把請求裡的 `site` 當成憑證，而它只是**宣告**。以下依嚴重度記錄。

### 一、跨工地隔離的四個缺口（全部已修，並以實測驗證）

1. **`op:deleteRecord` 的子層刪除缺工地範圍**（最嚴重）
   單據 id 是**全域主鍵**（`PK_labor`／`PK_equip` 只有 `id`），而回報／逐工種／
   稽核三張子表只以 `record_id` 為鍵。父表那道 `site_id` 條件擋得住父列、擋不住子列，
   因此「自己有權限的工地名 ＋ 別站的單據 id」會刪掉**別站的回報與稽核紀錄**，
   而且交易正常提交、不報任何錯。
   → `DeleteRecordRows` 開頭加一道「這筆單據是否屬於本站」的守衛；不屬於就直接返回。
   （子表都有 `ON DELETE CASCADE` 指向父表，父列不在本站＝本站沒有該刪的東西。）
   同一段刪除也被 `op:record` 使用，但那條路會因隨後 INSERT 撞 PK 而回滾，故只有
   `deleteRecord` 會真的落地——這也是它一直沒被發現的原因。

2. **附件下載完全沒有授權判定**
   附件分支寫在取得 `authz` **之前**就 return，且 SQL 條件是 `(@site = '' OR ...)`
   ——不帶 `site` 就恆真。等於「知道附件 id 就能下載任何工地的檔案」，
   把 `scope=all` 那邊的 stores 同步過濾與 `StripAudits` 真隔離整個抵銷。
   → `authz` 移到所有分支之前；權限一律以**描述資料所記的所屬工地**判定，不看呼叫者宣告。

3. **`op:uploadAttachment` 可覆寫他站附件本體**
   落檔是覆寫不是新建，帶著別站既有的附件 id 上傳即可把該站簽單照片內容換掉，
   而描述資料（檔名、大小、上傳日）不變——畫面上看不出來，對稽核等同**證據遭竄改且無痕跡**。

4. **`op:deleteAttachment` 忽略 `site`**，可刪任一工地的附件與其檔案。

   3／4 共用新的 `AttachSiteMismatch()`：描述資料那一列若存在，它的 `site_id` 才是權威。
   列不存在時放行是**刻意**的——前端的兩個正常流程（先上傳再存單、先存單再刪檔）
   都會在沒有列的狀態下呼叫；而要讓別站附件變成「沒有列」，本來就得先有那站的寫入權限。

### 二、授權的結構問題（root cause）

原本的寫法是「body 裡有 `site` 才檢查」——**有宣告才把關**，呼叫者只要不送 `site`
整段授權就被跳過。改為 `Wr.OpScopes` 的 op → 所需範圍對照表，**未登記一律拒絕**：
日後新增 op 若忘了登記，會在測試階段就被擋下，而不是安靜取得跨工地權限。

### 三、合約 §4.7 日期防呆補上伺服器端（原為唯一「合約要求做、程式沒做」項）

合約明訂地端 API 應重做前端的兩條檢查。**但只在這次請求真的改動了出工日或簽單繳回日時才驗**：
前端只在「回報送出」兩處檢查，成控**稽核儲存並不經過**——而稽核儲存同樣是整筆
`op:record` 覆寫。若每次寫入都驗，成控就無法對既有的違規舊單建稽核紀錄
（正式資料實查：1,120 筆單據中有 1 筆繳回日超期）。原樣重送放行、
任何想把值設成違規的請求擋下，兩邊都顧到。

### 四、其餘

- **日期格式化未指定 `InvariantCulture`**（計價紅線）：`yyyy` 取的是 CurrentCulture 的
  行事曆年份，Windows 區域設定可把 zh-TW 改成中華民國曆 → 年份輸出成 `0115`，
  整批日期靜默錯誤。同檔既有的 `TryParseExact` 已正確指定，可見是遺漏。數字解析同理。
- **每個 `/api` 請求都同步呼叫一次人資 API**：授權結果有快取，其前置的身分查詢沒有。
  新增 `CachingEmployeeDirectory` 裝飾層——否則人資系統會被本系統流量放大，
  且它一慢一停本系統立刻全面 503。
- **拒絕的授權結果也被快取 30 分鐘**：新到職者若在權限生效前先試登入一次，
  之後即使 ERP 已授權仍會持續被擋到快取過期，重登換瀏覽器都無效。改為只快取成功結果。
- **`Invalidate()` 從未被呼叫**：`op:master` 改動工地清單後補上，否則新工地對已登入的
  工地使用者最長 30 分鐘不出現，現場會誤判成「權限沒設好」。
- **無全域例外處理**：Production 回空白 500、Development 會把堆疊與 SQL 回給瀏覽器。
  補統一出口：記伺服器端日誌、只回固定形狀 JSON。
- **`AttachDir()` 每次呼叫都建目錄**，且被放在 `op:record` 交易內的逐筆附件迴圈中，
  等於在持有 `UPDLOCK`／`HOLDLOCK` 的臨界區做多餘檔案 I/O。改為程序生命期解析一次。
- `clearSite`／`clearAll` 的「尚待決策、無伺服器端權限檢查」註解已與階段 D 實作不符，更正。
