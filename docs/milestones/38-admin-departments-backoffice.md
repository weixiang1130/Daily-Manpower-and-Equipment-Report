# 節點 38：管理員部門改為後台可維護（v23.2）

## 背景

使用者裁示：預設管理員應為**成本管理部、採購處、總經理室**三個部門，
並詢問「上線後有沒有辦法自己在後台改」。

改版前 `Auth:AdminDepartments` 只存在 `appsettings.json`——要增減部門就得
請資訊處改設定檔並重啟服務。對一個「誰是管理員」這種會隨組織調整的設定來說，
每次都要走資訊處並不合理。

（順帶更正：先前記為「採購部」，實際是**採購處**。）

## 變更內容

### 一、管理員部門白名單改為資料庫存放、後台可維護

- 設定頁新增「管理員部門」區塊（管理員限定，一行一個部門）
- 經 `op:master` 的 `adminDepartments` 存入（合約 §4.1／§3.1）
- SQL 落點：新增 `app_settings` 通用鍵值表（**16 → 17 表 5 VIEW**）
- 權限模組 `Authorizer` 優先讀資料庫，快取至下次 `Invalidate()`

### 二、兩道刻意的保險

**① `op:master` 省略 `adminDepartments` ＝ 保留既有值，不是清空。**
這與 `sites` 的整包覆蓋語意刻意不同：舊版前端與其他呼叫端只送 `sites`，
若比照覆蓋，任何一次存設定都會把管理員設定洗掉。前端也對稱處理——
從未載入過該欄位時**不送這個鍵**，而不是送 `|| []`。

**② 資料庫沒有設定或為空 → 回退 `appsettings` 的預設值。**
避免有人在後台清空後把所有管理者一起鎖在門外。

### 三、部門名稱寫錯是靜默失敗，所以補了診斷

比對是 `StringComparer.Ordinal`，必須與人資 API 的 `deptName` 逐字元相符
（含全半形與空白）。寫錯不會報錯，只會讓該部門的人拿不到權限。因此：

- **啟動時**印出設定的管理員部門，供資訊處上線前肉眼核對
- **授權失敗時**記下該員**實際的部門字串**——設定寫「採購部」而人資回「採購處」
  這種情況才查得出來，否則現場只看得到一句「您在 ERP 尚無任何專案權限」

### 四、順手修掉的：地端 API 把中文全部逃脫成 `\uXXXX`

實作過程中發現的既有問題（不是這次改出來的）。.NET 的預設 JSON 編碼器會把
所有非 ASCII 逃脫，造成：

- 正式資料的 `scope=all` 實測 **905KB → 1,077KB，每次開站多 168KB（+19%）**
- 雲端 `api.mjs` 用 JS 的 `JSON.stringify`、不逃脫——**兩份實作的輸出格式不一致**
- 資料庫裡的中文也存成一整片 `\uXXXX`，資訊處打開表根本讀不出來

改用 `UnsafeRelaxedJsonEscaping`。名稱裡的 Unsafe 指「不對 HTML 敏感字元做額外
逃脫」，本 API 一律以 `application/json` 回應、不把回應嵌進 HTML，前端插入 DOM
前也一律走 `esc()`，故不適用該風險。

## 驗證（地端 13 項 ＋ 前端 6 項，全過）

**地端**（拋棄式資料庫＋ERP 替身，未觸碰既有測試庫）：

- 採購處、總經理室的人執行限管理員的 op → 200；工務部 → 403
- **省略 `adminDepartments` 再存一次，資料庫值前後完全相同**（關鍵語意）
- 送空陣列 → 資料庫清空 → 採購處的人**仍是管理員**（確認回退設定檔生效）
- 送 `[" 成本管理部 ", "成本管理部", "", "採購處"]` → 存成兩筆（去空白＋去重）
- 資料庫存 `["成本管理部","採購處"]`、API 回應與錯誤訊息皆為可讀中文

**前端**：載入既有值、管理員可編輯／一般使用者唯讀、儲存時去空白去重；
以及三種送出情境——從未載入過**不帶該鍵**、載入過帶值、刻意清空帶空陣列。
