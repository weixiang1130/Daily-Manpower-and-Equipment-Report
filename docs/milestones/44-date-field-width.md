# 節點 44 — 日期欄位寬度修正（現場回饋）

## 背景

現場回饋：**左上角的日期欄，雙位數的最後一碼會被擋住**，要確認日期還得再點開日曆看一次。

實測後確認**不是螢幕大小的問題，而是寫死的寬度上限**：

| 項目 | 寬度 |
|---|---|
| 文字「2026-08-18」（15px 字級，DM Sans） | 107.7px |
| 左右內距＋邊框 | 21.6px |
| Chrome `<input type="date">` 右側的日曆圖示 | 約 24px |
| **實際需要** | **約 132px** |
| 原本上限（`.field-num input{max-width:120px}`） | **120px** |

日期欄沿用了「數字欄」的 `.field-num`（1/6 版面＋輸入框限寬 120px）。數字欄放
「12.5」這種短內容綽綽有餘，但日期字串長得多，差的那 12px 剛好把最後一碼推到
日曆圖示底下。**與螢幕大小無關，所有人都會遇到。**

## 變更內容

- 新增 `.field-date`：版面欄寬由 2/12 放寬到 **3/12**，輸入框 `max-width:180px`
  （3/12 實測約 289px，對日期而言過寬，收斂後仍有約 48px 餘裕）。
- 點工／機具的**出工日期**與**簽單繳回日**四個欄位改用 `.field-date`。
- 全域補一道 `input[type="date"]{min-width:150px}`——**`min-width` 的優先權高於
  `max-width`**，因此這一條同時保護了散在清單、歷程報表、成控稽核篩選列的其他
  日期欄，日後新增日期欄也不會再踩同一個坑。

## 設計決策 / 取捨

- **不直接放寬 `.field-num`**：那會連「需求工數」等純數字欄一起變寬，版面留白變多。
  日期與數字的內容長度本來就不同量級，分開才是正確的歸類。
- **保留 3/12 的欄寬**：只加 `min-width` 而不放寬欄位的話，150px 的輸入框會撐在
  2/12 的格子裡擠壓鄰欄；連同欄寬一起調整才不會把版面推歪。
- **圖示寬度取 24px 估值**：`::-webkit-calendar-picker-indicator` 的實際寬度依瀏覽器
  與縮放而異，故不做精算，改以「需要 132px、給到 160～180px」的餘裕吸收差異。

## 影響範圍

`frontend/index.html`（4 個 class）、`frontend/style.css`（+10 行）。
**無邏輯變動、無資料結構變動**，app.js 完全未動。

## 驗證

以正式資料副本（地端 .NET ＋ LocalDB）實載，逐一量測**全系統 12 個日期欄位**
（點工／機具的申請與回報、兩張清單篩選、歷程報表起訖、成控稽核三處、設定鎖單日）：

| 欄位群 | 修正後寬度 | 需要 | 結果 |
|---|---|---|---|
| 出工日期／簽單繳回日（4 個） | 180px | 132px | ✅ |
| 清單／報表／稽核篩選（7 個） | 160px | 123px | ✅ |
| 設定鎖單日 | 220px | 132px | ✅ |

**12／12 通過、0 個被裁**；另確認無橫向捲軸、表單無溢出、console 零錯誤；
於 1024 寬的窄螢幕同樣完整顯示；**數字欄仍維持 120px 不受影響**。
