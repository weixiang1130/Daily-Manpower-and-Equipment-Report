# 節點 55 — 授權覆寫：ERP 之外的工地額外授予

**日期**：2026-08-24　**範圍**：`backend/onprem/dotnet/Auth.cs`、`Program.cs`（`/whoami`）
**資料庫**：無結構異動（沿用既有 `app_settings` 表）　**設定檔**：無異動

## 背景

工地可見範圍完全由 ERP 的專案角色決定（規則 4／5：專案代碼 → `sites.project_code` → 工地名）。
這條鏈只有兩個出口：管理員部門看全部，其餘依 ERP。**中間沒有任何位置可以說
「這個人，額外再加這個工地」。**

實際卡住的情境：某位工程師支援同廠區的另一棟，手上有那一棟的簽單要上傳，
但他在 ERP 只有原本那個專案的角色，系統忠實地不讓他看到另一棟——
系統行為正確，但業務走不下去。要解得等 ERP 端加專案角色，而那不是成本管理部能自己動的。

實查佐證：目前有工地角色的人之中，**約六成已經跨在兩個以上的專案**，
代表跨站支援是常態而非例外；但 ERP 端的調整有其流程與時間。

## 做法

在 `ComputeAsync()` 規則 5 之後，把一張**由成本管理部自行維護**的覆寫表併進可見工地。

存在既有的 `app_settings` 表（鍵 `site_grants`），**不另建資料表**——
維運帳號通常只有 `db_datareader`／`db_datawriter`，新增資料表要動 DDL、得另找 DBA。
沿用 `admin_departments` 已經證實可行的模式，讀取邏輯與容錯都有現成範本可抄。

```json
{
  "K0000000": {
    "sites": ["某工地", "另一個工地"],
    "by": "核准人", "at": "2026-08-24", "why": "支援原因"
  }
}
```

`sites` 必要；`by`／`at`／`why` 是稽核註記——**這張表沒有其他軌跡，是唯一的紀錄**。

## 三個設計決策

1. **只加工地，不升角色。** 被授予者在該站的角色仍是 ERP 算出來的那個
   （純靠覆寫進來的人視為 `SiteUser`）。不會因為被授予工地而變成主管或系統管理者。
2. **可以穿過規則 6。** 完全沒有 ERP 工地角色的人（新到職尚未進 ERP、支援性職務）
   也能靠覆寫進來。不開放的話，覆寫對最需要它的那群人無效。
3. **只加不減。** 不做「拿掉 ERP 給的工地」——權限撤銷應回到 ERP，
   在系統內做減法會讓「他為什麼看不到」變成要查兩個地方。

## 兩個實作上的關鍵

### 覆寫的比對以資料庫的工地名為準

JSON 裡打錯字的項目不會生效，也**不會憑空造出一個不存在的工地**。
比對大小寫不敏感，存回資料庫的正規名稱。

另外，取工地清單的 SQL 拿掉了 `project_code IS NOT NULL` 這個條件——
覆寫要能授予**尚未納管**（`project_code` 還沒填）的工地，在 SQL 就濾掉會做不到。
ERP 對映的部分仍然只認有 `project_code` 的列，`unmapped` 的統計不受影響。

### ⚠ 覆寫的快取必須有 TTL，不能只靠 `Invalidate()`

`admin_departments`（`_depts`）沒有 TTL 是可接受的：它極少變動，且變動時多半伴隨 `op:master`。

覆寫不一樣——它是「加完就要叫那個人馬上試」的操作。第一版照抄 `_depts` 的寫法（只靠
`Invalidate()` 清），**實測直接踩到**：測試流程先查了一次（把「空的覆寫表」快取住），
再寫入 `site_grants`，之後無論怎麼查都不生效。現場的表現會是「你加了我還是看不到」，
而且要等到有人去存一次工地設定才會好。

已改為與授權結果同一個 TTL（`Auth:CacheMinutes`），`Invalidate()` 仍會立即清除。
所以兩條生效路徑都有：存一次工地設定＝立刻，什麼都不做＝最多 `CacheMinutes` 分鐘。

## `/whoami` 診斷

新增 `grantedSites`／`grantNote`／`grantHint`。

覆寫製造了**第三種**「為什麼看得到／看不到這個工地」的成因（前兩種見節點 54）。
不標出來的話，日後查「他怎麼會看得到 X 站」會先去翻 ERP，而 ERP 上根本沒有這筆——
查修方向完全錯誤。`stoppedAt ③` 的訊息也一併補上覆寫這條路。

## 驗證

拋棄式本機庫（測畢已 DROP，未觸及 STAGING 與正式庫）＋ QAS ERP 唯讀連線，
`Auth:Mode=Dev`，五個案例：

| 案例 | 預期 | 結果 |
|---|---|---|
| ERP 有一個專案的人，未設覆寫 | 只看得到對映的那一站 | ✅ |
| 同上，覆寫加一站 | 兩站都看得到；`grantedSites` 只列覆寫來的 | ✅ |
| 覆寫含**打錯字的工地名** | 忽略，不產生工地 | ✅ |
| 覆寫含 **`project_code` 為 NULL 的工地** | 授予成功 | ✅ |
| **完全無 ERP 工地角色 ＋ 有覆寫** | 以 `SiteUser` 進入，只見被授予的站 | ✅ |
| 管理員部門 | `allSites`，不受覆寫影響 | ✅ |

角色在所有案例中都維持 ERP 判定的結果，沒有因覆寫而升級。

## 維運

- 寫入 `app_settings` 目前經 `op:master`（`OpScope.Admin`），只有管理員動得了；
  第一版以 SQL 直接維護，日後可做進設定頁
- 改完覆寫後到設定頁存一次工地設定即可立即生效
- **撤銷覆寫**：改該筆設定；若該人的權限應由 ERP 收回，請回 ERP 處理
