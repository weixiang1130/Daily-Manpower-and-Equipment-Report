# 節點 61：工地主管可刪除自己工地的已回報單（2026-08-28）

## 背景

節點 57 把「已回報單僅限管理員刪除」補上伺服器端把關後，工地主管覆核時發現錯單
也只能找管理員代刪。使用者要求賦予工地主管管理員權限；經確認範圍後**收斂為單一項能力**：
主管在**自己負責的工地**內可刪除已回報單。其餘管理員能力（跨站可見、改工地清單、
清空資料、稽核模組）一律不給。

## 決策一：主管身分**逐站**認定，不是逐人

`Role.SiteLead` 是整體角色，但一個人可能在 A 站是主任、B 站只是工程師。若用整體角色
判定，他在 B 站也會取得刪除權——那是越權。因此新增 `Authz.LeadSites`，逐站授予。

## 決策二：來源改用**白名單**，不採 ERP 的 Director 角色

第一版以 ERP `Director` 角色推導主管站，實查正式 ERP 後推翻：12 站共 20 人具該角色，
其中 **4 人涵蓋全部 12 站，且分屬總經理室／業務部／品保部／機電管理部**——都不是工地的人；
另有多筆部門與主管站對不上（部門在 A 站、卻是 B 站的 Director）。
**ERP 的 Director ≠ 現場工地主任**，直接採用會把「刪除計價依據」的權限發給總部幕僚。

改為成本管理部於**設定頁**維護白名單（`app_settings.site_leads`，形狀同 `site_grants`），
逐人逐站指定。與跨工地授權共用同一套解析、驗證與快取紀律。

三條邊界：

1. **白名單只在「本來就看得到的站」生效**——判定末端與可見工地取交集。
   白名單不授予可見性（要讓人看到工地請用跨工地授權），只把已可見的站升級成可刪。
   實測：白名單填了一個他看不到的站，`leadSites` 不含該站。
2. **鎖檔優先**：`LockGuard` 在 `ReportedDeleteGuard` 之前執行且不看主管身分，
   主管一樣刪不掉鎖檔區間內的單（結算凍結是實質控制）。
3. **管理員不受站別限制**：`CanDeleteReported = IsAdmin || LeadSites.Contains(site)`。

## 實作

- `Auth.cs`：`Authz.LeadSites` ＋ `CanDeleteReported(site)`；`LeadsAsync()` 讀白名單
  （TTL 快取，同覆寫）；`ComputeAsync` 以白名單比對工地名，末端與可見工地取交集。
  順手把共用讀取器 `ReadEmpSiteMapAsync` 的 `setting_key` 由**字串串接改為參數化**，
  並逐項 `GetValueKind` 判型（避免 SQL 直改塞入非字串元素時整份授權因例外而消失）。
- `Program.cs`：`ReportedDeleteGuard` 收 `Authz` 參數，改判 `!az.CanDeleteReported(site)`；
  403 訊息改為「僅限管理員或該工地主管刪除」。
- `Program.cs` `/whoami`：新增 `leadSites` ＋ **`canDeleteReportedScope`**（直接講出可刪範圍）。
  ⚠ 管理員的 `leadSites` 恆為空（規則 1／3 早退），只看該欄位會得出「管理員不能刪」的
  相反結論——節點 53／54 的教訓，故另給語意欄位。
- `Program.cs` `op:master`：新增 `siteLeads`（與 `siteGrants` 共用正規化 `NormEmpSiteMap`
  與 upsert SQL）；`OpScope.Admin` 已涵蓋，僅系統管理者可寫，讀取亦僅回管理者。
- `app.js`：新增 `AUTHZ` ＋ `loadAuthz()`（開站時與主資料並行取 `/whoami`）＋
  `canDeleteReported(site)`；點工／機具兩處刪除閘門由 `isAdmin()` 改用它。
- `index.html`／`app.js`：設定頁新增「工地主管白名單」面板（管理員限定，
  與跨工地授權共用 `parseSiteGrants`／`formatSiteGrants`）；順手補上兩份授權清單
  在非管理員時的 `readOnly` 鎖定（原本跨工地授權那格沒鎖，伺服器端本就擋得住，屬深度防禦）。
  **取不到 `/whoami`（雲端／`Auth:Mode=Off`／舊部署）一律退回 adminPin 行為**，
  與改版前完全相同。

> ⚠ **前後端必須成對**：後端放行但前端仍以 adminPin 擋，主管在瀏覽器就被擋住、
> 請求根本不會送出，整個功能形同虛設（本節點 code review 實際抓到此狀態）。

## 驗證（真實 ERP × 正式資料鏡像 × 瀏覽器）

**判定層**（白名單填兩站，其中一站該員看不到）：

| 身分 | 可見 | `leadSites` | 判讀 |
|---|---|---|---|
| 白名單工程師（ERP 無 Director） | 2 站 | 只有**看得到的那一站** | 白名單**不授予可見性** ✅ |
| ERP 全 12 站 Director、不在白名單 | 12 站 | `[]` | ERP 角色**不再**帶來刪除權 ✅ |
| 系統管理者 | 全部 | `[]` 但範圍顯示「全部工地」 | 診斷欄位不誤導 ✅ |

**執行層**（刪除已回報單，LocalDB 鏡像，正式庫全程未寫入）：

| 情境 | 結果 |
|---|---|
| 白名單成員刪**白名單站**的已回報單 | 200 已刪 ✅ |
| 同一人刪**可見但不在白名單**的站 | 403 ✅ |
| 同一人刪**鎖檔區間內**的單 | 403 鎖檔優先 ✅ |
| 前 ERP 全站 Director（已不在白名單） | 403 ✅ |
| 系統管理者刪任一站 | 200 已刪 ✅ |

**前端整合**（管理員於瀏覽器實測）：設定頁「工地主管白名單」面板可編輯 → 存檔 →
資料庫內容正確 → 授權**即刻改變**（存檔前可刪 A 站，存檔後改為可刪 B 站）；
console 零錯誤。另以主管身分**未輸入 adminPin** 實際刪除一筆已回報單並經資料庫確認消失。

## 上線後的維護方式

**預設沒有任何人在白名單上**（`site_leads` 鍵不存在＝行為與節點 61 之前完全相同，
已回報單僅限系統管理者刪除）。要授予時，由成本管理部於
**設定頁 →「工地主管白名單」**逐行填「工號｜工地｜原因」，存檔即刻生效
（`op:master` 會清授權快取）。撤銷就把該行刪掉再存一次。

⚠ 這份清單決定「誰能刪掉計價依據」，比跨工地授權更敏感：請只放該站真正的負責人，
並善用「原因」欄留下核准軌跡（這份設定沒有其他稽核軌跡）。
