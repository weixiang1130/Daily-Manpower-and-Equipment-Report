# 節點 65：點工三日回報鎖＋工地主管代處理權（2026-09-10）

## 背景

長官裁示：**點工限定三日內回報，沒有回報就直接鎖起來不給回報。**
使用者同時把主管的角色定為通則：「工地承辦要做什麼，都需要工地主管同意」——
承辦被擋的超常規操作（逾期回報、刪除已回報單等），一律由**該站主管**代為處理。

## 規則（與使用者對齊的三個口徑）

1. **期限**：出工日＋3 個日曆天內（含第 3 天）可回報，第 4 天起鎖。含週末假日照算。
2. **鎖了誰能救**：工地承辦（含一般工程師）鎖死；**該站工地主管**（節點 61 白名單）
   與管理員可代為回報——不另做「解鎖申請」流程，主管以自己的身分直接送出
   （送出前有確認框）。
3. **不溯及既往**：只鎖出工日 ≥ 生效日的單。否則部署當下所有超過 3 天的欠單
   瞬間全鎖，歷史帳永遠清不掉；舊欠單靠既有的追蹤提醒（20 天窗口）催繳。

⚠ **生效日暫定 `2026-10-01`**（`LABOR_REPORT_LOCK_START`／`Wr.LaborReportLockStart`，
前後端各一份、**必須同值**）：實際部署日確定後兩端同步調整再交付。

## 設計決策

- **只鎖「待回報→已回報」的送出，已回報單的編輯不受鎖**——節點 63 的稽核差異
  更正正是靠工地端事後修正數字；鎖編輯會把成控要的更正流程堵死。
- **僅點工**（使用者裁示）；機具不鎖。
- **主管代處理權收斂成通則**：`Authz.CanLeadOverride(site)`＝管理員或該站白名單主管；
  `CanDeleteReported` 改為委派給它。前端同構（`canLeadOverride()` 委派
  `canDeleteReported()`）。日後同類能力一律走這裡，勿另起爐灶。
- **伺服器端新舊出工日都查**（LockGuard 的教訓）：只查送進來的日期，
  把逾期單的出工日改成今天再送回報就繞過去了。
- 守衛順序：LockGuard（結算凍結）優先 → OverdueReportGuard——鎖檔是更強的控制，
  訊息以它為準。
- 雲端／`Auth:Mode=Off`：無伺服器把關（azl 為 null 不介入），前端以 adminPin
  作為代處理入口——與節點 61 的降級行為完全一致。

## 實作

- `Auth.cs`：新增 `CanLeadOverride(site)`；`CanDeleteReported` 委派之。
- `Program.cs`：`Wr.LaborReportWindowDays`／`Wr.LaborReportLockStart` 常數；
  `OverdueReportGuard`（op:record、僅 labor、僅送出回報；主管放行；
  查 stored status 已回報即放行；新舊日期都判）接在 LockGuard 之後。
- `app.js`：`LABOR_REPORT_WINDOW_DAYS`／`LABOR_REPORT_LOCK_START`／
  `laborReportLockError()`；開表單擋（承辦連表單都不給開，省得填完才被擋）；
  送出端再擋一次（表單可能跨日開著）＋主管確認框；清單狀態欄「🔒逾期」紅標
  （承辦看清單就知道要找主管）。`?ver=2026091002`。
- 合約 §4.7.1、AUTH-PLAN 角色表同步。

## 驗證

- 後端 `dotnet build` 0 警告 0 錯誤。
- 瀏覽器實載（stub 今日為 2026-10-06）六情境：逾期第 4 天鎖、期限日（第 3 天）不鎖、
  生效日前不溯及、已回報編輯不鎖、無日期不鎖——全數相符；
  `canLeadOverride` 五態（無身分無 PIN／無身分有 PIN／主管本站／主管他站／管理員）全對。
- 伺服器守衛的實測（403／主管放行／改日期繞鎖被擋）待 64＋65＋66 併包後
  於本機上線模擬環境一次驗證。

## MAX 審查修正（2026-09-10，與 64/66 同批）

1. **兩步繞過封堵**：審查抓到「編輯申請把出工日改成今天（存回待回報不經守衛、
   DateGuardError 對無 report 的存檔不驗）→ 再正常回報」可繞過鎖。
   OverdueReportGuard 加規則 2：逾期待回報單的出工日不得變更（僅主管/管理員）；
   前端申請送出成對攔截。
2. **參數改 app_settings 單一來源**（`labor_report_lock`，master.laborReportLock 下發）：
   生效日本就預定要改，雙常數必出同步縫；改期自此 UPDATE 即生效。
3. **雲端／Auth:Mode=Off 平價**：後端刻意不鎖，前端原本卻鎖（adminPin 成唯一逃生口）
   ——AUTHZ 為 null 時前端一律不啟用。
4. **邊界 1 改 isReported 口徑**（status 可能與 report 脫鉤，半殘單不得永久豁免）；
   **查無單且 baseV>0 放行**讓 409 deleted 出得來（403 會把「被刪」誤導成「被鎖」）。
5. 效能：生效日＋窗口前零查詢短路；3 個往返併成 1 個 JOIN 查詢；
   四守衛共用 TrySiteId()（唯讀，與會建站的 SiteId() 分清楚）。
6. UI：清單/追蹤提醒的 🔒 提示按身分分流（主管看到的不再是「請洽工地主管」叫他找自己）。
